01Overview

The Decision Maker determines which traffic phase gets the green light and for how long. The system uses two fixed phases: NS (North + South) and EW (East + West). Only one phase is green at a time.

Each cycle, the engine computes a priority score for both phases, picks the winner, calculates a stable green duration, and dispatches the command to physical lights via MQTT.

02Priority Score

For each phase, the engine aggregates both directions then computes a score in [0, 1] reflecting how urgently that phase needs green.

// aggregate both directions
weighted_score = score_dir1 + score_dir2
density = (density_dir1 + density_dir2) / 2

// normalize to [0, 1]
normalized = min(weighted_score / 200, 1.0)

// weighted sum
priority = 0.6 × normalized + 0.4 × density

α = 0.6 weights vehicle count (direct congestion). β = 0.4 weights lane density – this captures dense motorcycle clusters that YOLO may miss due to occlusion, detected instead by our hybrid Canny edge estimator.

03Green Duration

The winning phase gets a green duration calculated from its priority score, then adjusted for environmental conditions:

raw_duration = 10 + 40 × priority

// environment adjustment
env_factor = 1.0
  + 0.10 if temperature > 35°C
  + 0.05 if light > 900 lux

adjusted = raw_duration × env_factor

Base of 10s guarantees a minimum green even with zero traffic.

k = 40 means full congestion (priority = 1.0) yields up to 50s green.

04Smoothing & Stability

Raw durations can jump due to noisy image input. Exponential smoothing blends new values with history:

smoothed = λ × adjusted + (1 − λ) × previous

// cap maximum shift per cycle
if |smoothed − previous| > max_change:
  smoothed = previous ± max_change

// hard bounds
final = clamp(smoothed, 10s, 60s)

λ = 0.4: new reading contributes 40%, history 60%.

max_change = 10s: no single cycle shifts duration by more than 10 seconds regardless of traffic spike.
